ST185 ECU CAN setup checklist

Link G4X XtremeX TX frames 0x3E8-0x3F1 set to match the FROZEN center cluster. 2026-10-13. Research only; nothing changed in any repo. Cluster file = center-cluster-esp32-p4/main/canbus.c (main, 7d298c4). F1-F14 and N1-N6 = docs/research/CAN-SCALE-UNITS-AUDIT.html (OPEN-ITEMS row 32).

Count: 2 MUST SET, 23 VERIFY IN PCLINK, 9 OK. OK means the layout matches and I found no trap; it still has to be entered. RealDash reads only 0x3EF-0x3F1 plus the gear byte of 0x3EB (header of link_g4x_realdash.xml), so changing 0x3E8-0x3EE never changes a RealDash screen. The side clusters only get what the center forwards over UART.

Read first: how this was built

Built from Dan's own CAN docs: CANBUS-ENCODE-DECODE-REFERENCE.html in the center cluster repo (the "single canonical CAN reference"; called ref.html below), then CAN-BUS-ID-ALLOCATION-TABLE.md, link_g4x_can_setup.json/.lcs, CANBUS-LINK-G4X-CONFIG.md, CAN-CONFIG-STATUS.md, link_g4x_realdash.xml, REALDASH-LAYOUT.md, rd-build/BUILD-NOTES.md, tune/docs/PROTECTION_AND_WARNINGS.md, tune/limits.yaml, then checked against the frozen code (canbus.c, dash_data.c/.h, right cluster UI). Where a doc and the code disagree, the code wins and the row says so. See the last section for doc conflicts.
PCLink fields. ref.html:71 gives Dan's encode rule: wire = round(value × Mult ÷ Div) + Offset, and warns never to copy a DECODE number into PCLink. PCLink's user-stream fields are start position, width, byte order, Signed/Unsigned, Multiplier, Divider, Offset (HGM CompuShift + Link G4 guide), which matches. That page does not state the formula, so Dan's rule is the repo's, not Link's. Prove each raw number with PCLink's test calculator. The .lcs says "Confirm against PCLink G4X firmware ≥ 6.20 .lcs schema before importing" (link_g4x_can_setup.lcs:6), so enter channels by hand. I could NOT read Link's own G4X PCLink help: kb.linkecu.com and the Link support article do not cover these fields, and the vendor PDF (docs/vendor/XtremeXPlugInECUSpecs.pdf) only lists "On Board Baro" and "configurable math channels with up to four parameters".

Fix in ECU config

F1 · MUST SET · Boost reads wrong at altitude

The cluster always does (MAP − 100 kPa) × 0.145 (canbus.c:59-64). It assumes air pressure is 100 kPa. At your ~2,100 ft it is about 93.9 kPa (standard-atmosphere estimate; weather moves it ±3). So engine off it shows about −0.9 psi, and under boost it reads about 0.9 psi low. The 22 psi overboost flag on the side clusters uses the same number (right-side dash_data.h:171, alarm_task.c:37).
Fix: make a PCLink math channel = MAP − Baro + 100 (kPa). Send it on 0x3E8 bytes 2-3, unsigned 16-bit, mult 1, div 1, off 0. The cluster's subtraction then leaves true gauge boost at any altitude. Do not send plain MAP. Not yet proven: the exact baro parameter name, and that a math channel can add and subtract. Check: key on, engine off, cluster must read 0.0 psi.

F8 · MUST SET · Knock must be an instant flag

Any non-zero knock byte turns on the KNOCK warning and a 3,900 Hz beep (canbus.c:127, audio_alert.c:5). A knock level is almost never zero, so the red box and beep would stay on. The repo maps byte 0 to "Knock Level / Knock Limit" (link_g4x_can_setup.json:70); Link logs a knock level per cylinder (HP Academy thread).
Fix: send 0 normally and 1 the instant the ECU detects knock, with no delay on the way up (see the Knock section). I did not find the exact PCLink channel name. Pick it in PCLink and check the cluster stays quiet at idle.

F7 · VERIFY · Oil and fuel pressure must be gauge

The cluster converts kPa straight to psi with no air-pressure subtraction (canbus.c:86-87). If PCLink reports absolute pressure, the gauges read about 14 psi too high (about 13.6 at your altitude). The sensors are Lowdoller 7990150, 0-150 psi, 0.5 V = 0 (SENSOR-AND-ACTUATOR-REFERENCE.md:99); the repo never says gauge or absolute.
Test: key on, engine off, pump off: PCLink should read about 0 kPa. If it reads about 94 kPa, subtract Baro in a math channel and send that. A tiny negative value clamps to 0 on the cluster (dash_data.c:43,58).

F9 · VERIFY · Cruise and A/C numbers

RealDash shows words only for exact numbers: cruise 0-4 = OFF/STBY/SET/RES/OVR, A/C 0-3 = OFF/REQ/ON/FLT (link_g4x_realdash.xml frame 1007). Anything else shows "---". Nothing in the repo shows PCLink producing those numbers (the audit says A/C is a math channel). Build math channels that output exactly those values, then watch the RealDash tile. Cluster not involved.

F12 · VERIFY · Coolant pressure gauge vs absolute

RealDash alarms (150 kPa, then 250 or 200; see N6) assume gauge, and the XML only says kPa (link_g4x_realdash.xml frame 1008). Same engine-off test as F7: expect about 0 kPa, not about 94. Sensor: Ronybuy 150 psi (SENSOR-AND-ACTUATOR-REFERENCE.md:100). RealDash only; the cluster ignores it.

F14 · VERIFY · Fuel level must be 0-100 %

The cluster shows byte 1 of 0x3EB directly as percent (canbus.c:113). The channel is "An Volt 9" (link_g4x_can_setup.json:55). If it is not calibrated to percent, the left FUEL % arc shows volts as percent. The OEM float is 3 ohm full / 110 ohm empty and needs an external pull-up (SENSOR-AND-ACTUATOR-REFERENCE.md:102). Build the 0-100 table in PCLink; check empty, half, full.
Not fixable in the ECU (from the audit): N1 λ 0.9995-0.9999 shows "0.000" and boost/ign .95-.99 shows one low (right cluster, frozen); N2 center and left use different fuel and oil-temp thresholds; N3 keep RealDash on metric; N6 RealDash coolant-pressure alarm 250 vs 200. F2/F3 (°F/psi on clusters, °C/kPa on RealDash) are style only, and rule R65 says that is intended.

Boost gauge: vacuum vs boost

What the cluster really has. Boost is drawn on the right cluster only (center-cluster README.md:11; the center has no boost display). It is a horizontal bar on the round screen, "BOOST PSI", fixed range 0 to 30 psi (ui_bar_gauges.c:39). There is no scale artwork, no second unit and no inHg anywhere in the three cluster repos or the docs (searched; zero hits). Dan's guess is right: the bar is positive-only. The fill is clamped to 0-100 % (ui_bar_gauges.c:114-116), so vacuum gives an empty bar. The number above it is not clamped and prints a minus sign (ui_numeric.c:39-40), so vacuum shows as a negative psi number, e.g. "-9.4". I read the code; I did not run the firmware.
The math (fixed): psi = (wire kPa − 100) × 0.145038 (canbus.c:60,64). Over UART it is sent as (psi + 30) × 100, so vacuum down to −30 psi survives to the side screen (dash_data.c:88-89,150). Alarms use the same number: overboost flag 22 psi (dash_data.h:171), bar red 25 (right-colors.h:91), screen flash 28 (ui.c:44).
What the ECU must send: one value, MAP − Baro + 100 kPa, unsigned 16-bit. That single number gives the right negative psi in vacuum and the right positive psi in boost. At ~93.9 kPa air (estimate): engine off, plain MAP shows −0.9, fixed shows 0.0. Idle MAP of 35 kPa (example) shows −9.4 plain vs −8.5 true. 15 psi of real boost shows 14.1 plain vs 15.0 fixed. Do not send MGP, psi or inHg: the cluster does its own conversion and cannot change units.
If you want a negative scale on the bar or inHg: that is right-cluster firmware (frozen), a change to the 0.0 minimum at ui_bar_gauges.c:39 plus a reflash. ref.html:141-142 calls it a display-only change, which is true but still needs a reflash. Doc conflict: ref.html:151-152 says the 0-to-30 gauge "displays 0" at the key-on reading. By the code the bar is empty but the number shows the small negative.

Knock: where the gate lives

Cluster gate: none. Any non-zero byte 0 of 0x3EE sets KNOCK (canbus.c:127). There is no threshold, hold or latch, and no setting for it: the cluster's Kconfig only has a bench option that injects a fake knock (Kconfig.projbuild:188-193). The warning is rewritten from every 0x3EE frame (canbus.c:134, 50 ms per link_g4x_can_setup.json:67), so the red box disappears the moment the byte is 0 (ui_warning.c). The beep fires on each 0-to-non-zero change: 5 beeps/s for up to 5 s, stopping when all warn bits clear (audio_alert.c:48-50, 262-269, 292-297). So a flickering byte means repeated beep trains.
ECU gate: this is where to adjust it. Link's Knock Control compares measured noise to the Knock Target Table (0-1000, by rpm and load; "will reduce ignition advance when the actual measured level of engine noise is above the value in the Knock Target Table"), with Ign Retard Limit, Retard Gain, RPM/throttle lockouts, per-cylinder gains and per-cylinder detection on/off (Link G4+ manual, Knock Control Settings; I could not reach the G4X help itself, so confirm the names in your PCLink). "Knock Level Cyl X" is the raw measured noise, so it is almost never 0. That is why a level must not go in the byte (F8).
Recommend (updated: knock must never be delayed): byte 0 = a 0/1 flag that goes to 1 the instant the ECU's own knock detection fires (any cylinder over its Knock Target), with no delay, no minimum retard, no debounce on the way up. Only the way down may be held (about 1-2 s after knock stops, my judgment) so the beep does not re-fire; a hold on release delays nothing the driver needs. Keep false alarms down in the ECU (Knock Target Table, gain, lockouts), not with a delay. Do not trigger on accumulated retard: retard is the ECU's reaction and can lag the event. Do not send Knock Level or a limit value.
Latency chain I can account for: ECU detects, then waits for the next 0x3EE slot (50 ms, link_g4x_can_setup.json:67; set it to 10 ms like 0x3E8 to cut the worst case, which also means updating the JSON/.lcs/ID table and running check_parity.py), then the center decodes at once (canbus.c:127), the beep task polls every 40 ms (audio_alert.c, warn_monitor_task), and the right cluster redraws on its ~50 ms paint tick (ui_signal_filter.c:12). I did not measure the center-to-right UART delay. Tension to review: the base map deliberately uses a high knock cut threshold (limits.yaml:12-16, STREET_DRIVE_LIMITS.md:33). The warning flag is separate from the cut, but the timing-pull reaction is the ECU's retard settings, which need checking for speed too. Not found: the exact PCLink name of the knock-detect channel (the manual page lists "Knock Level Cyl X" and "Knk Ign Trim CylX" tables). Check the PCLink parameter list.

Send metric numbers (°C, kPa, km/h); the cluster converts to °F/psi/mph itself (canbus.c:41-44, 64, 85-87). I could not confirm in Link docs how PCLink display units feed a user-defined CAN channel, so set PCLink to metric and check each value with the test calculator. G1-5: do B30 and B28 need an optoisolator?

Answer: NO optoisolator on either pin. Read the 12 V directly, pull-up OFF, active HIGH.

Why R56 does not apply here. R56 is about inputs that need ground-active (the CSB3 inputs S7/S8, DECISIONS.md:96). A G4X digital input is different: Link lists "Each channel independently configurable with pull-up resistors and active state control" for the XtremeX digital inputs (docs/vendor/XtremeXPlugInECUSpecs.pdf, Digital Inputs list). So active-HIGH is a setting, not a workaround.
Thresholds. (Link mod, G4X Xtreme WireIn thread) "The switching thresholds on the DI's are fixed by hardware ... From memory it needs to rise above about 1.8V to be considered active, and fall below about 1.0V to be considered inactive." A real G4X Xtreme wire-in owner wired +12 V switch signals straight into DI7 and DI8 (clutch and brake) and the clutch input worked (same thread). A 12 V signal is far above 1.8 V.
Pull-up. A pull-up is for ground-switched inputs. For a 12 V-active signal, switch it OFF, per a forum user's reply for a normally open switch fed from +12 V: Pullup OFF, Active state HIGH (search summary, not re-read; confirm in PCLink). A Link mod says the DI pull-up is to 12 V (search summary), so leaving it ON would hold the input active whenever the line floats.
  • B30 (DI7 start request, ST1 lead): NO optoisolator. Already planned right: pull-up OFF (sot/channels.csv b30). Set Active = HIGH in PCLink.
  • B28 (DI9 IG2 sense): NO optoisolator, but fix the pull-up. sot/channels.csv b28 says sel-4k7-to-12v. For a 12 V-active sense that should be OFF. This is a conflict between that row and the advice above. Set Active = HIGH.
One real risk. A 12 V-active line that is "off" can float or leak. In the thread above, a brake line read 3.39 V with the switch off (above the 1.0 V inactive limit), which is why the DI stayed active. Link's fix: "A pull-down resistor connected to ground might be enough" (mod). So measure each line with the key off: it must read under 1.0 V; if not, add a pull-down. No resistor value is given by Link.
Not found: a maximum input voltage for a G4X DI in any Link document I could reach (PCLink help needs an ECU connected). The same forum shows 12 V going into DIs, and a mod says 12 V is fine into an analog input (threshold thread), but that is not a rating. Check the XtremeX wiring manual in PCLink for charging-voltage (about 14.4 V) tolerance before you close G1-5.

  • Send rate. (mod) "The maximum rate for transmitting CAN messages out of the ecu ... is limited to 200Hz" (thread). It is a G4+ thread, about 8 years old; I found nothing G4X-specific. Your repo already sends 0x3E8-0x3EA at 10 ms, so 10 ms for 0x3EE is not a new load level. Confirm the Transmit Rate range in PCLink once the ECU is connected.
  • How the numbers combine. (mod) Use the PCLink test calculator to prove each Multiplier/Divider/Offset ("often easier to do it by trial and error"). On G4X, a value received from CAN is treated as the displayed value, not the stored one (thread). That is about receive (0x3EC/0x3ED), but it means test the receive channels too.
  • Boost reference. Math channels subtract parameters (e.g. "Boost error = Target Boost - MAP", math channel list) and run at 1000 Hz. Another poster notes MAP is absolute and you need a baro reference for gauge pressure (CAN gauge thread, from search summary). So MAP − Baro + 100 is a normal math channel. The exact baro parameter name is still unconfirmed; the XtremeX has an on-board baro sensor (spec PDF).
  • Knock detection (G4X, 3S-GTE example). (mod) The ECU reads "knock level" per cylinder, set by gain, listening frequency and the Knock Threshold table. A mod says signal-to-noise is what matters, and to confirm a spike by briefly adding advance (thread). So false alarms are fixed in the ECU (gain, frequency, threshold table), as I recommended. I still found no G4X channel that outputs a ready-made "knock happened" 0/1. Plan to build it as a math channel from knock level vs the threshold, and test it on the bench. A forum user also says CAN is poor for knock timing because it must be synchronous with the crank (thread, search summary): this flag is for the driver warning only.
